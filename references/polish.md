# 阶段 5：润色

目标是让译文读起来像中文作者写的，同时一点信息都不少。

## 和 cn-humanizer 的关系

如果环境里装了 `cn-humanizer`，它的 `references/translation-guide.md`（12 种翻译腔）和 `references/cn-ai-vocabulary.md`（AI 词表）可以直接参考。但是**不要照搬它的改写尺度**。它面向博客和通用文本，鼓励加个人观点、用第一人称、留点不完美，示例也会把原文压缩成几句口语（比如把一段技术说明缩成"跑了一圈 benchmark，效果不错"）。放到书里，这就是漏译和改写作者。

| 可以吸收 | 书籍翻译里不能用 |
| --- | --- |
| 拆长句，减少"的"字串 | 删信息、合并压缩论点 |
| 被动改主动，名词化改动词 | 加入译者的观点和反应 |
| 删多余的代词和连接词 | 第一人称插话（除非原文就有） |
| 语序改成"先背景后动作" | 把学术文体改成聊天口吻 |
| 英文俗语换中文说法 | 故意留"不完美"，或为了节奏改写事实 |

## 怎么改

**拆长从句。** 这是最主要的工作。英文一句带几个从句，中文拆成几个短句，靠语序和语义衔接：

> 原：尽管这项在方法论上存在一些值得商榷之处的研究，由于其在该领域所取得的突破性进展以及对后续研究可能产生的深远影响，仍然被认为具有重要的学术价值。
>
> 改：这项研究的方法论有可商榷之处，但它在该领域取得了突破，对后续研究也可能影响深远，因此仍被认为有重要的学术价值。

（注意：所有信息都还在。cn-humanizer 那种"成果确实有突破，学术价值还是有的"在这里就压缩过头了。）

**把生硬的英文表达换成中文的说法。** 英文俗语、比喻换成中文的俗语、成语、歇后语、典故，或者干脆用平实的中文。要点是意思和语气都对得上，并且符合当时的场景：

| 英文 | 直译腔 | 可用的中文 |
| --- | --- | --- |
| the pot calling the kettle black | 锅嫌壶黑 | 五十步笑百步 |
| kill two birds with one stone | 用一块石头杀两只鸟 | 一箭双雕 / 一举两得 |
| let the cat out of the bag | 把猫从袋子里放出来 | 说漏了嘴 / 露了馅 |
| the elephant in the room | 房间里的大象 | 人人心知肚明却没人提的事 |
| a storm in a teacup | 茶杯里的风暴 | 小题大做（语境合适时也可保留，这个说法中文已通行） |
| burn the midnight oil | 燃烧午夜的油 | 挑灯夜战 / 开夜车 |

原文不是英语时思路相同。比如德语 "mit dem Kopf durch die Wand" 说的是硬闯行不通，可以译成"一意孤行碰钉子"之类，不要只看字面，也不要选意思偏了的俗语。

用多少，看读者是谁（阶段 0 定下的）：

- **供学术研究**：少用。原文的比喻、典故尽量照原样译出，稍微生硬一点也可以，读者要靠它回到原文的语义。不要拿中文成语替换原文的意象。
- **给大众阅读**：可以多用、活用。作者平实的论述，只要意思分毫不差，也可以用中文现成的说法来表达（“换了名字本质没变”→“换汤不换药”；“代价最后落到工人身上”→“羊毛出在羊身上”）。用户要求“多用”时，就照这个方向放开。

不管用多少，这几条分寸都要守：

- 用之前查清这个说法的本义、褒贬、轻重，不望文生义。成语常带额外的判断和程度，作者没说的意思不能借成语加进去。拿不准就不用。
- 定义和推理的环节概念要准，比喻放在说理的前后，不放在定义上。
- 一句不堆两个成语，一段别变成四字排比；不写文言腔。同一章里同一个说法不超过一次。
- 用到的成语、俗语、典故记成清单（一行一条：段号、说法、对应的原文），整理成用例表给用户把关，也方便全书查重。
- 口语和网络用语不是禁区：贴切、表达到位、又不是烂梗的，可以用。但要先弄清原文那个词是专名、历史名词，还是普通说法，专名不能按字面意思发挥。
- 歇后语、俏皮话要看作者本身的语气，通常用在小说和通俗作品中。
- 中国语境的俗语会带来中国的画面。如果书里写的是别国的场景，避免用太有中国特定典故的说法（"三顾茅庐"放进罗马史里就很跳）。
- 表达方式有隐含的时代感和阶层感，小说人物要说符合他身份的话。

**改句子的骨架，不只是换字。** 给大众读者的书，读一句，如果能一眼还原出英文的语法结构，就要重写。只换字词、骨架还是英文的，读者照样觉得是翻译腔。常见的英文骨架和改法：

| 翻译腔 | 怎么改 |
| --- | --- |
| 作为 X，他…… | 他是 X，……；或者直接删 |
| X，其 Y…… | X 的 Y……；或拆句 |
| 分裂句（“使它名声扫地的，是……”） | 主谓直说：Z 让它名声扫地 |
| 被动加施事（“这种局面被掩盖了，掩盖它的是……”） | 主动说：……掩盖了这种局面 |
| 具有……的重要性；发挥……的作用；扮演……的角色 | 动词直说：很要紧；管用；干了什么 |
| 对……的分析、批判、理解（名词化） | 还原成动词：分析……、怎样理解…… |
| ……的过程、……的方式、……的事实 | 大多可删 |
| 一种……、某种……（英文冠词） | 删：一种深刻的矛盾→矛盾很深 |
| 这一、该、此 | 这、这个；或重复名词；或省略 |
| 在……方面、就……而言、从……的角度 | 直接说 |
| 抽象名词作主语（“这一认识导致了……”） | 人作主语：人们认识到……，于是…… |
| 形容词叠加（深刻的、根本的缺陷） | 从根子上就有毛病 |

拆长句时，先说事再评事，按时间和因果排：先背景后动作，先原因后结果，先条件后结论。一个小句（到逗号）一般不超过 20 字，长定语拆出去单独成句。也别走到另一头：满篇七八个字的短句像电报，要长短相间。学术研究用的书，这一节只用来消除读不通的地方，不必大改骨架。

**其他翻译腔：** "进行了讨论"→"讨论了"；"在……方面有所提升"→"……提升了"；"通过使用这种方法"→"用这个方法"；"它……它……它……"→省略主语；连续的"然而""此外""因此"，语义已经清楚时就删；"被"能去就去；一句超过三个"的"，就拆开或调整定语。

**AI 腔也要除：** 意义拔高（"具有里程碑式的意义"——除非原文确实这么说）、空洞收尾、"值得注意的是"这类提示语。用 `style` 看信号：

```bash
python <skill>/scripts/booktool.py style . --chapter 03
```

这些只是提示，不是硬指标。学术书的长句和"此外"不是一律要改；统计只帮你定位，判断还是靠读。

## 不能动的东西

- **事实和立场**：作者的判断、语气强度、限定条件都不要改。别把"必然"改成"可能"，也别把"可能"改成"必然"。不替作者弱化尖锐的表达，不添加防御性说法。
- **已落实的引文**：一字不改（`polish-check` 会对照台账检查）。学术书里的所有引号内文字通常也不动，要改得回原文确认。
- **译名**：以术语表为准。
- **段落和注释的顺序**，以及数字、日期。

遇到疑问就回原文。润色时发现的错译、漏译要修正，这是收获之一，不只是"改得好听"。

## 流程

1. 备份基线：

   ```bash
   python <skill>/scripts/booktool.py polish-start .
   ```

2. 按顺序逐章读，**对照原文**改。不要只看中文就改，只看中文容易把意思改偏。每章读完更新 `project.json` 的 `progress.polished_chapters`。

   改动多的时候（比如整章重写去翻译腔，或者分给几个子代理并行），用 `polish_tool.py` 逐段提交：

   ```bash
   python <skill>/scripts/polish_tool.py pairs . 07 1 30          # 调出第 1—30 段的英中对照
   python <skill>/scripts/polish_tool.py apply . 07 polish/07-a.md # 只写要改的段：<!--b014--> 下面跟这段新全文
   python <skill>/scripts/polish_tool.py lint . 07                 # 长句清单、翻译腔信号，同基线比
   ```

   `apply` 拿每段同润色基线比，注号、作者出处、数字、引号内文字、引文块、已落实的引文有变化的段一律退回，不写入，并说明原因；其余的写回。它带文件锁，几个子代理可以同时改同一章的不同段。`lint` 把不计引文超过 50 字的句子都列出来：这些不是非拆不可，但每句都要单独看一遍，拆了明显更好就拆。先由主控亲手改一章当样稿，定下力度，再分给子代理。

3. 每章（或每批）改完校验：

   ```bash
   python <skill>/scripts/booktool.py polish-check . --protect-quotes
   ```

   它对比基线，检查：锚点和顺序不变；改过的段落数字不变；台账里已落实的引文还在；加了 `--protect-quotes` 时，每段引号内的文字不变；并把每处改动的前后文写进 `polish/polish-log.json`。**小说的对白在引号里，本来就要润色，不要加这个参数。**

4. 全书改完再跑一遍 `check` 和 `audit-check`。

## 请用户把关的地方

做一张改动对照页给用户看，删去的标红、新写的标绿，每段标明改动落在作者正文、引号内还是注释，可附英文原文：

```bash
python <skill>/scripts/diff_review.py . --base baseline --en                 # 对比当前润色基线
python <skill>/scripts/diff_review.py . --rev HEAD~3 --chapters 07 12       # 对比 git 某个版本
```

默认写到 `build/改动对照.html`。事实核查、补注、勘误之后同样用它，用户最关心“改的是原文还是注释”。

把这几类选一些让用户过目，不用全部：替换了俗语或成语的段落、改写过的笑话、语气变化大的段落。用户的修改意见归纳成规则写进 `project.json`，再回头按规则看全书。

## 三道独立复核

润色改得越多，越容易改出新错，而且改的人自己看不出来。所以大改之后要过三道复核，每道都交给没参与前一步的子代理，分章并行。每道都要求回报：改了哪些（文件、段号或注号、原文→改后，一行一条），哪些拿不准、留给主控决定。

1. **润色后对原文复核。** 逐段对照原文看改稿，专找改偏的地方：限定词丢了（“one of the first”成了“最早”）、语气被加重或减弱、指代不清、成语用错了意思（比如把预兆说成“前车之鉴”）、信息漏了。
2. **终审，专查实质译错。** 不管文笔，只看意思：倍数和增减（“增长了 3.5 倍”和“增长到 3.5 倍”）、并列被译成条件、时间先后弄反、否定范围、书名和专名误译、数字和年代。
3. **分发前通读校对。** 只读中文，像出版社校对一样一字一句读完，注释也读。不润色，不改写，只找：错别字、漏字多字、读不通的句子、半角标点、引号括号书名号不成对、同一专名前后写法不一、注释和正文对不上、给读者看的注释离开上下文读不懂、年份数字前后矛盾。引文里的旧式用字（“那末”“底”）不改。

主控逐条看回报再定，拿不准的交给用户。

## 完成标准

- 全书每章都对照原文读过一遍（`polished_chapters` 覆盖全部）；
- 三道独立复核都做过，回报都处理了；
- `polish-check`、`check`、`audit-check` 通过；
- `polish/polish-log.json` 记录了所有改动。
