# 阶段 3：逐章翻译

## 先试译定调

正式开始前，选第一章开头约 2 页，或者最有代表性的一节，译成样稿，放到 `zh/` 之外（比如 `logs/sample.md`），请用户看一眼。确认后把语气要点写进 `project.json` 的 `user_preferences`。这份样稿就是全书的风格基准，后面的章节或子代理都要先读它。

按体裁定基调：

- **学术、非虚构**：流畅的中文学术文体。作者语气强就保持强，不替作者缓和，也不加防御性说明；作者的讽刺要保留下来。
- **小说**：对白要活，每个角色说话要有区分度，叙述要有文学感。同人或改编作品贴近原作官方中文的语感。笑话如果直译后不好笑了，可以换用中文里现成的笑话或另写一个，前提是用户同意过，并记入 `logs/decisions.md`。
- **其他**（通俗、工具书、回忆录）：先看原文的正式程度，别把随笔译成论文，也别把论文译成随笔。

## 文件格式

译文放在 `zh/`，**文件名和原文一致，锚点也和原文一致**：

```markdown
<!--b001 p.37-->
# 第3章 第一阶段

<!--b002 p.37-->
土地改革从北方开始。[1]各地进度并不一致……

## 注释与引用

1. W. Hinton, *Fanshen*, New York, 1966, p.12.
```

- 保留所有锚点，一个原文段对应一个译文段。中文确实需要时，一个锚点下可以分成两段，但不要把两个锚点合成一段。
- 章标题写成 `# 第3章 第一阶段` 这样，序言、附录不写"第 N 章"。排版脚本靠这个区分章节和前言后记。
- 注释区标题固定为 `## 注释与引用`。

## 注释的规则

- 每章从 1 开始连续编号，正文 `[n]` 和注释条目一一对应。
- **说明性文字译成中文，书目信息保留原文。** 书名、文章名、刊名、作者、出版社、地点、日期、页码、网址保持原样，便于读者回查：

  ```markdown
  3. 关于这一数字的争议，参见 W. Hinton, *Fanshen*, New York, 1966, p.12；作者在此处低估了华北的情况。
  ```

- 校注、译者注一律放进章末注释，不要夹在正文里，正文只留注号。需要新增注释时按出现顺序重新编号。
- **事后插注、删注用脚本，不要手工改编号**。手工改很容易出错：后面的注号漏改；紧跟的“同上”指到新注上；“编者注373”这种书里的编号被误改。

  ```bash
  python <skill>/scripts/notes_tool.py add . 07 "<正文里只出现一次的锚定文字>" "<注释正文>"
  python <skill>/scripts/notes_tool.py remove . 07 12
  python <skill>/scripts/notes_tool.py lint .        # 编号连续、注释里写了段号、“同上”指错、注号放在句号后
  ```

- 注释里不要写段号（读者看不到），尽量不用“同上”，写“同注N”或写全出处。注号放在句末标点前面。
- 提到人名时：注释的书目部分保留原文，说明文字里按术语表译。
- **写注时就分清两类注释。** 出处、版本、译法差异这类学术注释只进完整版；帮普通读者看懂正文的说明（人物、事件、术语的背景，原书的事实错误）是读者注释，写的时候就在末尾加 `<!--读者-->`，阅读版会保留（见 [assembly.md](assembly.md)）。事后再整本分类要费很多工夫。

## 翻译的方法

**每章动笔前**：读 `project.json`、`glossary/glossary.csv`（至少是本章相关部分）、`logs/decisions.md`，再通读本章原文。读完再译，因为指代、伏笔和语气都要看完才知道。

**翻译时**：用中文的语序和节奏把意思说出来，不要逐句对译。这一遍就可以处理明显的长从句和直译腔，不用全留给润色；但这一遍的首要目标是准确和完整。

**遇到以下内容：**

| 情况 | 处理 |
| --- | --- |
| 引文 | 已知有中文原文或中译本的（比如《资本论》《毛泽东选集》），这时能查就查；查不到先译出，加 `【原文待核】`，留给阶段 4 |
| 原文明显有错（日期、前后矛盾、书目） | 按阶段 0 定下的方式：默认照译，在章末加校注说明；用户选了勘误的，正文直接改，注里说明原书怎么写的。观点性的分歧不算错，不改 |
| 双关语、文字游戏 | 优先找中文对应的说法；实在不行，学术书用注释说明，小说按用户的授权改写 |
| 外文原词确有必要保留的 | 括注原文，首次出现时括一次，不要反复括 |
| 数字 | 准确第一。大数按中文习惯用"万""亿"，换算后复查 |
| 拿不准的意思 | 回查上下文和外部资料。仍不确定就在章末校注或 `logs/decisions.md` 里说明，不要含混带过 |

**每章译完**：

```bash
python <skill>/scripts/booktool.py check . --chapter 03
```

处理所有错误，逐条看警告。警告不一定是问题，但有两类必须回原文核对："译文偏短"很可能是漏译；数字换算成"万""亿"后被报告的，脚本不会验证换算对不对，要自己算一遍。不足 20 个词的短段和注释的说明文字，脚本不查长度，通读时留意。然后通读一遍译文，更新 `project.json` 的进度，把本章定下的处理方式记入 `logs/decisions.md`。

## 长章和全书的节奏

- 单次输出放不下一章时，按锚点分段写入（比如 b001–b060、b061–b120），写完一段立刻落盘，不要攒着。
- 一次任务做不完就停在章节边界，并把进度写清楚，不要为了赶进度压缩内容。如果是额度或长度不够，就告诉用户到第几章了，下次从哪里继续。
- 全书的完成是以 `check` 通过的章数算的，不是以"感觉差不多"算的。

## 用子代理并行时

环境有子代理时可以按章并行，这样快，但语气容易漂移。每个子代理的任务说明要写明：项目目录、要译的章节文件、输出路径、风格样稿路径、术语表路径、本文件路径，以及必须跑 `check` 并通过。主代理收到结果后要抽读，不能只看子代理的报告。子代理发现的新名字先记到自己的结果里，由主代理统一查证入表，再回填，否则几个子代理可能各译各的。

**同一本书的前几章建议串行译**，语气和术语稳定之后再并行。小说和叙事性强的书尽量串行。

## 完成标准

- 所有章节 `check` 无错误，警告都看过；
- 没有占位符、概括或"此处略"；
- 全书译名以术语表为准，暂译已记录。
